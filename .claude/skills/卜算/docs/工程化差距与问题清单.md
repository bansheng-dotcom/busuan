## 一、一句话结论

**广度与输出规范是全参考系最强的，推演规则的可检验性与测试守护深度是全参考系最薄弱的。** 盘排得对、话讲得严、覆盖 16 术 17 事类；但「断得对不对」这一层几乎全靠 LLM 临场发挥，没有 `tianzhi-core` / `liuyao` / `qimen-dunjia` 那样的机器可核验闭环。

## 二、对标参考系谱系（8 项目 = 4 工程层级）

| 层级 | 项目 | 核心能力 | 我们与它的关系 |
|---|---|---|---|
| 纯 prompt 技能 | `bazi-pan-skill` / `liuren-skill` / `mingli-skills` | 排盘脚本 + 断语库 + 分阶段 SOP | 已借 MIT（`pan/` 目录源自 dglijin-oss） |
| **核心算法库** | `tianzhi-core` | 纯函数 + 全测试 + **断语写成判定条件** + **对拍** | 方向一致，深度差一档（**主对标**） |
| MCP 知识库 | `liuyao` | 6 书手切 SQLite + 原文哈希 + RAG + 多 harness | 已集成其 MCP 作六爻主断 |

| 产品/应用 | `mingli`(Rust/WASM) / `mingyu`(App) | 完整产品化 | 不对标 |

对标应锚定 **`tianzhi-core`（推演+工程化标杆）** 与 **`qimen-dunjia`（单术 SOP 标杆）**，这是最该补的两块。

## 三、四大能力维度差距

### 3.1 工程化 —— 最大短板

| 维度 | 我们 | 标杆 |
|---|---|---|
| 测试文件 | 3 个 / 1039 行（`tests/regression_test.py` 839、`architecture_test.py` 113、`doc_path_test.py` 87） | tianzhi-core 每模块一个 test 文件 |
| 测试性质 | 40 个 `test_*` 函数，但都是**抽样单点 golden**（如 `test_liuren_golden`、`test_qimen_keying`、`test_rules`） | **断语逐句做成判定条件 + 典籍实例回归**（648 句紫微断语、六壬 48 课起例、卷三实例） |
| 对拍 | 紫微「算法移植 iztro」+ py-iztro 排盘对照；六壬 `--ref` 独立九宗门；七政「诚实近似」 | **与 iztro 对拍数千盘**、六壬 48 课逐课核对三传 |
| 知识库形态 | Grep 典籍 txt + `references/` 23 个速查表（静态 MD） | liuyao 手切 SQLite（原文绑定页/行/列/**哈希** + 校订记录 + 盘面核对状态）；qimen 4 个 JSON 强制查表 |
| 文档与实现 | 两处来源，`doc_path_test` 只查「路径存在」不查「语义一致」 | tianzhi-core `catalog` 从代码 docstring 现读，「文档与实现只有一处来源」 |

**三个具体缺口**：

1. **没有「断语 → 判定条件 → 出处」这条机器可核验的链**。`judge/` 有 21 个模块、规则函数返回 `{judgment, confidence, evidence, basis}`，但每条规则「忠实原文与否、有无出处、判定条件是否可测」三个维度无人守护。tianzhi-core 的核心理念是「把推演过程摊开让人检验」——我们摊开了盘面，没摊开推演。

2. **没有「对拍」回归**。六壬 `--ref`（`libs/regress/liuren_regress.py`）是「自写 vs 自写」的独立九宗门对照，不是「自写 vs 公认实现」；紫微只有「算法移植 iztro」的标注，没看到「数千盘逐星对拍」的测试数据；七政四余（`libs/pan/qizheng.py`）明确标「无统一可代入时间的公式，取通行近似」。这导致「排盘对」之外，「算得对不对」无法证伪。

3. **知识库是「文档」不是「可检索库」**。`references/` 速查表是静态 MD，判词靠 LLM 现场 Grep。liuyao 的教训关键：**「检索条件和资料字段修复不等于预测准确率提升」**（它做了 8 例成对试验承认无增益）——我们缺的正是这种「我到底有没有用」的自我评估。

### 3.2 文本输出 —— 我们最强，但有两个隐患

诚实结论：**输出规范这一项，我们碾压参考系**。四层证据（代码/映照/原文推演/逻辑）+ 三级结论标注 + 七级评级 + 白话两层 + 表格白话列 + 免责 + 诚实边界，比 `qimen-dunjia` 的 9 步 SOP 还厚。

**隐患一：缺「独立 evaluator 强制终审」的硬闸。** qimen 明确「没有 evaluator 报告 = 未完成」；我们虽有 `libs/judge/bazi_evaluator.py` / `libs/judge/ziwei_crosscheck.py`，但**没要求每次必跑，也没有「不跑就标注降级」的强制闭环**。我们的规范是「写得很严」，qimen 是「跑得必须」——前者靠自觉，后者靠机制。

**隐患二：白话层可能变成第二个自由发挥点。** tianzhi-core 的理念是「模型只负责把结果说成人话，幻觉就没有落脚点」——白话应是**翻译代码/原文结果**，不是模型再断一遍。我们的白话层规范（「只翻译、不得新增吉凶定性」）方向写对了，但缺可执行校验，目前只是文字约束。

### 3.3 古籍调用 —— 差在「校订」和「出处固化」两层

| 维度 | 我们 | liuyao / tianzhi-core |
|---|---|---|
| 检索 | Grep 423 份 txt + `classical_search` 段落 ID + `case_search` TF-IDF | SQLite 原文绑定页/行/列/**哈希** + 校订记录 + 盘面核对状态 |
| 出处 | 「书名:行号」+ `--passage-id` 回查 | 出处标签逐条指回独立典籍仓库（tianzhi-classics） |
| 出处来源 | LLM 断卦时**临时 Grep** | **每条规则在代码里固化出处** |

核心差距：我们的出处是「断卦那一刻临时搜出来的」，liuyao/tianzhi-core 的出处是「规则定义时固化进去、可机器回查」的。前者依赖 LLM 每次别搜错，后者是结构保证。

### 3.4 推演能力 —— 规则化率低，且「不判」没清单化

- **旺衰量化是离散分、非连续比**：`libs/judge/bazi_evaluator.py` 用 `score = 得令×3 + 得地 + 得生 + 得助×2` → 标签；tianzhi-core 是 `strength.ratio 0.453` 连续值 + 五档 label。连续 ratio 可跨盘比较、可检验，我们没暴露。
- **流派分歧显式化覆盖严重不足**：实测带 UND/流派/分歧/近似标注的 `pan/` 模块只有 6 个——`bazi.py`、`bazi_liunian.py`、`meihua.py`、`qimen.py`、`qizheng.py`、`zhiwei.py`；**六爻、六壬、太乙、风水、择日、金口诀、小六壬、纳甲等 11 个术的流派分歧是隐式的**（只在 `SKILL.md` 口头列了 `--zishi`/`--dst`/`--ref`/`--miaowang`，代码层没显式化）。
- **「不判」没清单化**：tianzhi-core 有 `ziwei.SKIPPED`（6 条格局按安星法永不成立、不判）；我们有「无信号组」（学历/性格/外貌/精确年份）的**问题类别**级诚实边界，但没有**「某条具体断语在盘上判不了就逐条不判并写明缘故」**的规则级清单。

## 五、事类覆盖诊断：不是缺能力，是「入口与能力脱节」

**核实后的事实（比「缺事类」更精确）**：

`SKILL.md` 第三节「按问事推荐」路由表只有 17 类，但底层速查表已经覆盖了更细的事类——

| 速查表 | 已覆盖事类数 | 路由表 17 类里没暴露的细类 |
|---|---|---|
| `references/六壬分类占断速查.md` | 11 类 | **求子/孕产**、交易/合作 |
| `references/奇门分类占断速查.md` | 14 类 | **盗贼、远信、迁移、行人归期、官禄升迁、官司牵连、胜败** |
| `references/梅花十八类占.md` | 18 类（天时~坟墓） | **天时/天气、坟墓/风水、失物细分** 等 |

**结论：底层能力已经有了，是主路由表没接到。** 用户问「怀孕」「找盗贼」「等远信/等消息」「想搬家移民」「问行人归期」「明天天气」时，速查表有对应断法，但 `SKILL.md` 的 17 类路由表接不住，会被错误地塞进「终身命理」「失物·寻人」「出行」「国运」等粗类里。

**具体缺口清单**（按「应拆细 / 应新增」分类）：

- **应拆细**（合并过粗、用神不同）：
  - 失物·寻人 → 拆「寻物 / 寻人（走失、归期）/ 寻宠」（用神不同：寻物看财爻、寻人看子孙/官鬼、归期看父母爻/驿马、宠物看子孙）。
  - 健康 → 拆「病势 / 问药问医 / 问住院」（六壬已有「制鬼之位乃良医」）。
  - 国运大事 → 拆「主客胜负 / 选举 / 天灾」（太乙主客已有，现代对应需补）。
- **应新增**（速查表已有、路由表缺，或传统高频但完全空白）：
  - 求子/孕产（六壬「天喜临身主有喜」已备）
  - 盗贼/失窃（奇门「占盗贼」已备）
  - 远信/等消息（奇门「占远信」已备）
  - 迁移/搬家/移民（奇门「占迁移」已备，现塞在「出行」）
  - 行人归期（奇门「行人归期」已备）
  - 天气（梅花十八类「天时占」已备；天文占是「星象灾异」不是「明日天气」）
  - 交易/签约/谈判（六壬「交易/合作」已备，现塞在「求财」）
  - 牢狱/刑非（现塞在「官司」）
  - 贵人/小人、同事关系（六爻兄弟爻/奇门值符可断，无入口）
  - 学业细分（选校/留学方向，现塞在「考试」）

> 建议：路由表从「17 类」升级为「17 主类 + 约 10 个高频子类」的**两级表**，每子类标主荐术法 + 用神/类神，把速查表已有的细类接回入口。

## 六、我们自身问题全清单（按严重度编号，供排期）

> 每条含「证据 + 对标 + 现状」，可逐条勾销。`取象优化升级.md` 已单列的射覆取象 5 条根因不再重复。

**P0（结构性短板，堵「断得对不对无法证伪」）**

1. **推演规则无逐规则测试**。40 个 `test_*` 是抽样 golden，`judge/` 21 个模块缺「逐规则出处 + 判定条件 + 测试」。对标 tianzhi-core（断语→判定条件→回归）。
2. **无对拍回归**。六壬缺《六壬大全》48 课起例回归；紫微缺 iztro 逐星对拍；七政四余近似无天文对拍。对标 tianzhi-core。
3. **断语规则化率低**。绝大多数断语仍靠 LLM 临场发挥，`judge/` 只覆盖少数规则（体用生克/奇门格局/六壬天将等）。对标 tianzhi-core「648 句紫微断语写成判定条件」。

**P1（能力闭环缺失）**

4. **缺独立 evaluator 强制终审**。`bazi_evaluator`/`ziwei_crosscheck` 存在但非强制、无「不跑就降级」硬闸。对标 qimen-dunjia。
5. **奇门缺排盘自检 verify**。无 qimen-dunjia 的 144 项自检 + 决策树修复流程。
6. **白话层无可执行校验**。「只翻译不得新增定性」仅文字约束，缺机制。对标 tianzhi-core「模型只说人话」。
7. **流派分歧显式化只覆盖 6/16 术**。11 个术（六爻/六壬/太乙/风水/择日/金口诀/小六壬/纳甲等）的流派分歧是隐式的。对标 tianzhi-core（分歧做成参数）。
8. **事类路由表与速查表脱节**。见第五节，路由表 17 类没接到速查表已覆盖的孕产/盗贼/远信/迁移/天气等细类。

**P2（深度加固）**

9. **古籍调用无「校订/哈希」层**。423 份 txt 缺「版本校订记录 + 盘面核对状态 + 原文哈希」。对标 liuyao。
10. **出处是临时 Grep、非规则固化**。对标 tianzhi-classics（出处标签逐条指回原文）。
11. **文档与实现两处来源**。`doc_path_test` 只查路径存在，不查「SKILL.md/docs 写的规则 ↔ `judge/` 代码实现的规则」语义一致。对标 tianzhi-core `catalog`。
12. **无「案例检索是否有用」的自我评估**。liuyao 做了 8 例成对试验承认检索无主方向增益；我们 1300 则案例 + `case_search` 无等效评估。
13. **旺衰量化未暴露连续 ratio**。离散标签（旺/衰）无法跨盘比较。对标 tianzhi-core `strength.ratio`。
