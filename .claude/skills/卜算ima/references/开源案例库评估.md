# 开源案例库/工具评估（补现有流程）

> 目标：评估开源项目能否补进现有流程「cast.py 起盘 + 案例库 search_txt.py 检索 + 后验回填（cases/manage.py / feedback.py / trace.py）」。
> 评估日期：2026-10-08。来源：GitHub 公开仓库 + 检索摘要。

## 结论速览

| 项目 | 类型 | 对你现有流程的价值 | 建议 |
|---|---|---|---|
| [zhishengyk/liuyao](https://github.com/zhishengyk/liuyao) | 六爻 MCP：RAG 相似卦例检索 + 古籍原文 SQLite + 本地排盘 | **高**（补「语义相似检索」短板） | 借鉴 RAG 检索思路，或复用其古籍 SQLite |
| [opencode-tianji](https://himcp.ai/server/opencode-tianji) | 六爻插件：381 古籍卦例 + benchmark 346 例 + 梅花模块 | 中（卦例仍是古籍；benchmark 思路可借鉴） | 借鉴 benchmark 评测，升级你的后验统计 |
| [banderzhm/ZhouYiLab](https://github.com/banderzhm/ZhouYiLab) | 多术排盘引擎（六壬/六爻/紫微/八字/奇门/梅花） | 低（排盘与 cast.py 重复） | 仅作排盘交叉校验对照 |

## 详评

### 1. zhishengyk/liuyao —— 价值最高
- **有什么**：预建古籍数据库（原文+校订+盘面核对状态）、**RAG 语义相似卦例检索**、原文回查、本地离线排盘、SQLite 存储、支持 Claude Code 等多 Harness。
- **对你的价值**：你现在检索相似案例靠 `search_txt.py` 关键词（「求财/病/官」），是**字面匹配**；它的 RAG 是**语义相似检索**——能解决「缺同类案例」时捞不到近义课体/卦例的短板。
- **建议**：不一定要整包接，**借鉴思路**——给 `案例库` 建一个向量索引（embedding），检索时「关键词 + 语义」双路，命中同类案例的概率更高。其古籍 SQLite 若含校订原文，也可复用。

### 2. opencode-tianji —— 借鉴 benchmark
- **有什么**：六爻 381 则卦例库（仍是《增删卜易》《卜筮正宗》古籍）、346 例金标准评测基准、13 工具、8 部古籍全文溯源。
- **对你的价值**：卦例是古籍（非现代）；但其「**benchmark + 金标准 + runner**」的思路值得借鉴——你现在有 `cases/manage.py stats` 的**后验统计**，可升级成**固定评测集**（选一批问题当金标准，定期跑命中率）。
- **建议**：借鉴 benchmark 结构，把你的后验案例固化成评测集。

### 3. banderzhm/ZhouYiLab —— 仅作对照
- **有什么**：多术排盘引擎，数字卦生成。
- **对你的价值**：`cast.py` 已有排盘，重复度高。唯一用处是**交叉校验**（两套排盘对照，防止单引擎算错）。

## 结论：三条腿补全

| 短板 | 补法 |
|---|---|
| **检索**（缺同类案例捞不到） | liuyao 的 RAG 思路 → 给案例库加向量/语义检索 |
| **评测**（命中率靠手数） | opencode-tianji 的 benchmark 思路 → 后验固化成评测集 |
| **现代案例**（无现成公开集） | 无捷径，靠「自己积累 + 后验回填」（见 `现代案例取象速记.md`） |

> ⚠️ 开源项目里的「卦例库」**绝大多数仍是古籍**（增删卜易、卜筮正宗），**现代带反馈案例公开数据集基本不存在**——这是现状，不是哪个项目的问题。
